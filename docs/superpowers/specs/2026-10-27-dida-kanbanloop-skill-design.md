# Dida Kanbanloop Skill 设计规格

- 日期：2026-10-27
- Work ID：W3
- 需求基线：用户已在任务简报中批准；后续按自主执行授权推进，不增设例行设计确认暂停
- 本文范围：Skill 设计与验收，不包含本轮代码或 Skill 实施

## 1. 目标与权威需求

### 1.1 目标

交付一个可由 OpenCode 加载的自包含 Skill。每次调用只处理用户指定的一个 Dida365／滴答清单（TickTick）父任务，把实际项目工作、可见子任务进度和 Kanban 人工审查闭环连接起来。

### 1.2 用户明确提出的要求（权威基线）

以下 ID 在规格、计划和验收中保持不变；后续设计决策不得削弱这些要求。

- **UR-1**：交付物是 OpenCode Skill，调用开始时使用 Dida365/TickTick MCP。每次只处理用户以“清单/项目 + Kanban 看板 + 任务”指定的一项任务；缺少目标信息时，必须在任何变更前主动询问缺失项。
- **UR-2**：目标看板具有名称严格为 `处理中`、`待审查`、`已完成` 的工作流列。开始工作时，只把父任务移动到 `处理中`。读取父任务及每个子任务的标题和描述，根据内容与用户习惯决定顺序，通常先完成子任务。
- **UR-3**：子任务只有在实际完成后才能标记完成。工作期间仍按用户既有习惯更新本地项目/文档进度；同时推荐或落实一组有序的、可见的 TickTick 子任务，并随实际完成动态更新。由 Skill 创建的子任务标题必须以 `[Agent]` 结尾。子任务绝不能在列之间移动，只允许其完成状态发生变化。
- **UR-4**：所有请求工作完成后，绝不能完成父任务；只能把父任务移动到 `待审查`，然后停止。用户审查通过后自行移动到 `已完成`；若拒绝，用户更新父任务描述并移回 `处理中`，Skill 再开始下一轮。
- **UR-5**：README/首次使用指引必须明确要求三个看板列名精确为 `处理中`、`待审查`、`已完成`，并展示建议显示顺序 `处理中` → `待审查` → `已完成`；名称不得改动，视觉顺序不作运行时强制。

### 1.3 简报中已明确批准的设计约束

- **DC-1**：缺失或不匹配的看板列不得由 Skill 静默创建或改名；必须询问/停止并解释。
- **DC-2**：优先采用自包含根 `SKILL.md` 与 README 安装/使用说明，不引入运行时代码或依赖。
- **DC-3**：合适时复用现有子任务并避免重复；父任务绝不能由 Skill 完成。
- **DC-4**：没有 MCP 证据不得声称 Dida 变更成功。
- **DC-5**：MCP 缺失、权限不足、清单/看板/任务匹配歧义或必需列不匹配时，必须在 unsafe changes 前停止并报告。

### 1.4 本次设计补充的假设与决策（非新增用户需求）

- **AD-1 交付形态**：落实 DC-2，仓库根目录使用一个自包含 `SKILL.md`，README 提供安装和使用说明；不增加运行时脚本、依赖、安装器或持久化服务。
- **AD-2 列解析**：三个工作流列 `处理中`、`待审查`、`已完成` 必须各存在且名称完全匹配一次；不按空白修剪、不模糊匹配，空白或近似名称不能替代必需列。**不要求看板只有三列**：其他列可以存在，但不参与本工作流，必须被忽略且永不被修改。显示顺序由 README 指导，运行时使用解析后的列 ID，不靠视觉位置推算状态。
- **AD-3 子任务定义**：子任务指 `parentId` 等于目标父任务 ID 的 TickTick child task，不是 CHECKLIST 的 `items`。描述检查同时覆盖 `content` 与 `desc`；空字符串也是已读取的有效内容。
- **AD-4 看板身份**：已验证 MCP 以 `projectId` 列出列，没有独立的看板枚举接口。用户给出的看板必须能唯一绑定到该项目的列集合；无法唯一绑定或项目明确不是 Kanban 时停止，不猜测。
- **AD-5 完成证据**： “实际完成”必须有当前工作项的可观察产物、测试结果或复现结果；仅开始、创建子任务、写入计划或主观判断不算完成。
- **AD-6 有序可见步骤**：先把有序步骤呈现在正常进度/计划中；复用合适的现有子任务，不为同一步骤重复创建。新建子任务使用 `N. <动作> [Agent]` 标题，`N` 从 1 起反映计划顺序，后续新增步骤取下一个未用编号；已有任务不为编号或后缀而改名，也不重排。
- **AD-7 本地进度习惯**：目标项目的适用 `AGENTS.md`/`CLAUDE.md`、已有文档与已召回用户习惯决定本地进度更新方式；Skill 不强制另建进度文件，TickTick 镜像不能取代正常本地工作流。
- **AD-8 审查状态重入**：父任务已在 `处理中` 时幂等恢复，不重复移动；调用时父任务仍在 `待审查`/`已完成`，或不满足 active（即 `status != 0`），则不启动新一轮。只有用户按 UR-4 把拒绝的父任务移回 `处理中` 后，才根据新描述重入。若仅按标题查找而未在 active 任务中找到父任务，必须要求显式任务 ID 来区分“未找到”和“已结束”；只有凭 ID 读取到 `status = 2` 或 `status = -1` 才能报告已完成/已放弃，始终零写入。
- **AD-9 文档级验证边界**：构建阶段用静态检查和明确的场景变更账本走查验证指令契约。没有专用测试任务及实时 MCP 证据时，不声称已完成真实滴答清单端到端验证。

## 2. 方案比较与收敛

| 决策点 | 候选方案 | 权衡 | 选择及理由 |
|---|---|---|---|
| 交付架构 | A. 自包含提示型 Skill；B. 本地状态机脚本；C. Skill 加常驻同步服务 | B/C 可强制部分状态约束，但引入依赖、凭证面、状态存储和无关运维；A 最符合单任务、调用式工作与 AD-1 | 选 A；用严格的 MCP 调用白名单、写前守卫、写后证据和场景验收降低提示型方案的执行风险 |
| 列缺失处理 | A. 自动创建/改名；B. 解释后停止，由用户配置 | A 可能改坏既有看板且违反已声明假设；B 保留用户对看板的控制权 | 选 B；README 预先给出三个精确名称与顺序 |
| 子任务计划 | A. 每轮全部新建；B. 只口头推荐；C. 复用合适项，仅补缺失项 | A 在重试/重入时产生重复；B 不可见、不能动态完成；C 同时满足可见性和幂等性 | 选 C；新建项以 `[Agent]` 标记来源，以编号表达顺序，已有项保持原样 |
| 完成与审查 | A. 全部完成父任务；B. 父任务进入 `待审查` 后停止 | A 绕过人工审查且直接违反 UR-4 | 选 B；`已完成` 只能是用户审查后的手动动作 |

**收敛结论**：采用“一个根 `SKILL.md` + README + 无仓库内测试运行时”的方案。任何自动化便利都不能突破父/子任务权限边界；无法证明目标、数据完整性或写入结果时，宁可停止并报告。

## 3. 范围与非目标

### 3.1 范围内

- OpenCode Skill 元数据、触发说明和完整单任务工作流。
- Dida365/TickTick MCP 目标解析、看板校验、父子任务读取和受限写入。
- 有序子任务的复用、补建、实际完成同步，以及正常本地进度习惯保留。
- 人工审查、拒绝后重入、中断恢复、失败/重试与证据报告。
- README 安装、MCP 前提、精确列配置、调用示例、审查/拒绝说明和故障排查。
- 无外部依赖的静态检查及不触碰真实任务的场景走查。

### 3.2 非目标

- 批量处理多个父任务、跨项目移动、自动同步整个看板或后台轮询。
- 自动创建、删除、重命名或重排项目/看板列。
- 重开、删除、放弃、改期、指派、改标题、改描述或重排任何子任务；创建后的子任务仅允许按本规格完成。
- 完成父任务、替用户通过审查、自动把父任务移入 `已完成`，或替拒绝任务改写父描述。
- 把 CHECKLIST `items` 当作 child tasks 修改。
- 引入凭证、运行时依赖、通用 API 包装器、安装脚本或无关重构。

## 4. 状态模型与不变量

### 4.1 父任务闭环

```text
调用与只读预检
      │ 首次且仅父任务的必要写入
      ▼
   处理中 ── 实际工作 + 子任务按证据完成 ──▶ 待审查 ── Skill 停止
                                               │
                              用户通过：手动移至 已完成
                                               │
                              用户拒绝：更新描述并手动移回 处理中
                                               ▼
                                      再次调用，开启新一轮
```

- `已完成` 是用户审查后的看板位置，不是 Skill 可执行的终点。
- Skill 不通过完成父任务来表达工作完成；父任务在整个 Skill 调用中保持 `status = 0`。
- 已在 `待审查` 的父任务表示等待人工决定，Skill 不自动拉回；已在 `已完成`、`status = 2` 或 `status = -1` 的父任务不被重开或移动。

### 4.2 必须始终成立的不变量

1. 一次调用只锁定一个 `projectId + parentTaskId`，不操作第二个父任务。
2. 在任何写入前，目标、写权限、看板绑定、三个列和父子任务读取完整性均已通过检查。
3. 父任务唯一允许的字段变更是以 `update_task` 设置 `columnId`；禁止传入父任务 `status`。
4. 对子任务禁止调用 `update_task`、`move_task` 或批量完成接口；允许 `create_task` 补建和对已核实的 child ID 调用单个 `complete_task`。
5. 子任务的 `columnId` 不由 Skill 设置或修改，完成前后应保持不变；不得通过“再移动一次”修复异常列变化。
6. 父任务永远不能成为 `complete_task` 或批量完成接口的参数。
7. 每次成功报告都必须对应 MCP 成功响应中的目标状态，或对应的写后读取证据；调用已发出不等于成功。

## 5. 精确工作流

### 5.1 调用与只读预检（零写入）

1. **立即使用 MCP**：确认 `dida365` 工具可用。不可用、未认证或目录不可读时停止，说明配置阻塞；不用本地文字模拟同步。
2. **补齐目标**：从用户输入取得清单/项目、Kanban 看板、父任务。缺任何一项时，用一次简洁问题索取全部缺失项；在答案到达前不做任何 Dida 或项目工作变更。
3. **唯一解析项目与看板**：用 `list_projects(offset, limit)` 分页并以精确名称或明确 ID 匹配项目，不能用首个模糊结果。调用 `get_project_with_undone_tasks(project_id)` 检查项目、`viewMode`、`permission` 和任务范围。项目名称重复、看板无法唯一绑定、`viewMode` 明确非 `kanban` 或权限不是 `write` 时停止。
4. **校验列**：用 `list_columns(project_id)` 按名称精确解析 `处理中`、`待审查`、`已完成`，三者各恰好一个且属于该项目。缺失、重名、项目不一致时停止并说明用户应如何手工修正；禁止调用列写入接口。
5. **唯一解析父任务**：若用户提供明确任务 ID，直接用 `get_task_in_project(project_id, task_id)` 读取；否则只在目标项目的 active 任务中按精确标题查找，标题不唯一时请求任务 ID。若标题没有 active 匹配，不得猜测它是“未找到”还是“已结束”，应零写入报告“未找到 active 父任务”并要求显式任务 ID；凭 ID 读取后，不存在/项目不匹配才报告“未找到”，`status = 2` 或 `status = -1` 则分别报告“已完成”或“已放弃”。任何情况下目标都必须是顶层任务（无 `parentId`）、属于目标项目且 `status = 0`；若 `parentId` 非空，说明用户选中的是子任务，零写入并要求提供顶层父任务。若当前在 `待审查`/`已完成` 或状态非 active，按 AD-8 停止；其他 active 位置或 `处理中` 均可进入下一项检查。
6. **完整读取父与全部子任务**：先用 `get_task_in_project(project_id, task_id)` 读取父任务完整 `title`、`content`、`desc`，再通过以下两个独立只读分支枚举 child，最后按任务 ID 合并；不得用 `get_project_with_undone_tasks` 代替 abandoned 或 completed 的完整性证明。
   - **active + abandoned 分支**：调用 `filter_tasks({ filter: { projectIds: [projectId], status: [0, -1] } })`，不传 `kind` 或日期限制，筛选 `parentId = parent.id` 的全部 active（`0`）与 abandoned（`-1`）child。该工具不可用时，或响应错误、截断、达到已知上限、完整性无法确认时，零写入停止；不得退回 undone-only 快照并声称完整。
   - **completed 分支**：用 `list_completed_tasks_by_date` 在项目内查询 `status = 2` 的历史并筛选同一 `parentId`。若 MCP 或用户提供可靠父创建时间，以其为 `startDate`、当前时间为 `endDate`；否则先进行 `projectIds` 限定、无日期收窄的初始查询，避免捏造起点。若服务要求显式日期或初始查询被截断/达到上限，要求用户提供覆盖父任务整个生命周期的范围，再以连续、无间隔的完成时间窗口查询；任一窗口仍 capped/truncated、同一时间窗无法继续细分或范围完整性无法证明时，零写入停止。
   - **逐任务读取与分支汇合**：对每个 child 再用 `get_task_in_project` 读取完整 `title`、`content`、`desc`、`status`、`parentId`、`columnId`；空 `content`/`desc` 是已读取的有效空值，不是漏读。abandoned 只读取、不重开或完成。若两个分支的快照对同一 ID 给出冲突身份/状态，重新读取；仍冲突或任一分支无法证明“每个子任务”均已覆盖时，明确缺口并零写入停止。

只读检查全部通过后才允许进入首次写入。这样即使后续发现读取不完整，也不会留下半个看板迁移。

### 5.2 开始工作：只处理父任务列

1. 记录父任务当前 `columnId` 和子任务的列基线。
2. 若父任务不在 `处理中`，第一次变更只能是：
   `update_task(task_id = parent.id, task = { columnId: processingColumn.id })`。
   不提交其他父字段，不触碰任何子任务。
3. 若父任务已经在 `处理中`，跳过冗余写入。
4. 用成功响应中的 `id + columnId + status`，必要时再用 `get_task_in_project` 写后读取，确认父任务位于 `处理中` 且仍为 `status = 0`。无法确认时停止，不开始子任务创建或本地任务工作。

### 5.3 内容驱动的工作顺序与可见子任务

1. 根据父任务和每个子任务的标题/描述、依赖关系、目标项目规则和用户习惯制定顺序；通常先完成子任务，再做父级集成与验证，并说明关键顺序依据。父任务下所有 active 子任务默认都在本轮范围内，只有用户明确排除时才可缩小；abandoned 项保持原状态，既不算 active 待办，也不能由 Skill 改成完成。
2. 按 AD-7 维护正常本地计划/进度；不额外发明一套进度文档。
3. 把尚未完成的实际工作和必要验证映射为有序可见 child tasks。复用合适的活跃现有项；若一个已完成 child 的产物和当前验证仍能证明它满足本轮要求，保留并计为已完成，**不得再创建重复 Agent child**。只有无法确认仍满足时，才按最新要求补建具体修正项，且不得重开旧项。
4. 只对没有合适现有项的步骤调用 `create_task`，字段限制为 `projectId`、`parentId`、`title`，以及可选的初始 `content`。标题采用 `N. <动作> [Agent]`；不得传 `columnId` 或 `status`。
5. 不创建用于“移动父任务到待审查”或“等待用户审查”的 Agent 子任务，因为这些不是可由 Agent 完成的实际工作项。已完成的预检也不倒补成待办。
6. 计划变化时补充新的有序子任务并继续复用；不重编号、不改写已有项。失去必要性的任务不能伪装完成，应保持 incomplete/active 并报告其 ID 与原因，由用户决定放弃/删除或明确排除；在用户处理前，它仍阻止父任务进入 `待审查`。

### 5.4 执行与动态同步

对每个工作项依次执行：

1. 完成真实本地工作及该项目要求的验证/进度记录。
2. 取得 AD-5 所定义的完成证据；没有证据就保持子任务 active，不进入完成调用。
3. 写入前用 `get_task_in_project` 重新读取待完成项，核对 `taskId` 仍是预期 ID、`projectId` 匹配、`parentId = parent.id`、当前 `status = 0`，并记录其 `columnId`；任一不符都不得调用完成接口。
4. 只调用 `complete_task(project_id, child_id)`，不使用批量接口。已有用户子任务也可在完成真实工作后完成；不能因其没有 `[Agent]` 后缀而另建重复项。
5. 以成功响应或写后读取确认 `status = 2`、`parentId` 未变、`columnId` 与完成前一致。字段不足时必须补读；发现异常列变化时停止并报告，不能反向移动子任务。
6. 只有证据和 MCP 状态都成立，才在正常进度中报告该子任务完成。随后处理下一项，必要时按 5.3 补充后续步骤。

### 5.5 结束：只进入待审查并停止

进入终点前必须同时满足：

- 父任务最新描述和当前轮次全部请求工作已实际完成，所需验证已有真实结果。
- 所有当前轮次计划内/范围内子任务均已完成并有 MCP 证据；没有遗漏的活跃必需步骤。只有用户明确排除或原先已 abandoned 的子任务可不计入待完成集合，且必须在报告中说明；Skill 不得自行排除、放弃或静默忽略。
- 正常本地项目/文档进度已按既有习惯更新。
- 重新读取父任务，确认它仍是同一任务、`status = 0`，且没有需要先处理的并发状态冲突。

随后仅执行 `update_task` 把父任务的 `columnId` 设为 `待审查` 的列 ID。确认返回/回读仍显示 `status = 0` 后，简要报告实际工作、验证、子任务同步和“等待用户审查”；如有排除项，报告还须逐项列出原先 abandoned child 的 `taskId + status = -1`，以及用户明确排除 child 的 `taskId + status = 0 + 用户排除原因`，不得把这些状态变化记在 Skill 名下。然后停止，不得再创建子任务、继续做无关工作或完成/移动父任务到 `已完成`。

## 6. MCP 交互契约

| 工具 | 用途与关键参数 | 写入边界/成功证据 |
|---|---|---|
| `list_projects(offset, limit)` | 分页解析清单/项目 | 只读；名称不唯一即消歧，不取首个近似项 |
| `get_project_with_undone_tasks(project_id)` | 读取项目、Kanban/权限、active 父任务候选和列快照 | 只读；不得用它证明 abandoned 或 completed child 已完整枚举 |
| `filter_tasks({ filter: { projectIds, status: [0, -1] } })` | 枚举项目内 active + abandoned child；不传 `kind`/日期以免漏类 | 只读；不可用、错误、达到已知上限、截断或完整性不明时零写入停止，不以 undone 快照代替 |
| `list_columns(project_id)` | 精确解析三个工作流列 | 只读；每个必需名称恰好一个匹配，额外列忽略且不修改 |
| `get_task_in_project(project_id, task_id)` | 读取父/子完整标题、`content`、`desc`、状态、父子关系和列；按显式 ID 区分未找到/已结束；必要时写后核实 | 只读；ID 与项目必须匹配 |
| `list_completed_tasks_by_date(search.projectIds, startDate/endDate, client_timezone)` | 按父创建时间或用户确认覆盖父生命周期的范围枚举 completed child，支持去重和重入 | 只读；无可靠起点时先项目限定无日期查询；需要日期或 capped 时获取完整范围并无间隔分窗，任一截断/缺口即零写入停止 |
| `update_task(task_id, task: { columnId })` | 仅父任务进入 `处理中` 或 `待审查` | 父任务专用；成功响应或回读必须证明目标列和 `status = 0` |
| `create_task(task: { projectId, title, content?, parentId })` | 创建缺失的有序 Agent child task | 只允许这四个字段（`content` 可选），不传 `columnId/status/sortOrder/dueDate/tags` 或其他字段；核实返回 ID、项目、父子关系、精确后缀和 active 状态 |
| `complete_task(project_id, task_id)` | 仅完成已实际完成的 child task | 禁止父 ID/批量完成；核实 `status = 2` 且 `columnId` 未变 |

Dida 状态值固定为：`0` active、`-1` abandoned、`2` completed。`create_column`、`update_column`、`move_task`、任务删除/放弃/重开以及批量完成均不在本 Skill 的允许调用集合内。

## 7. 失败、重试、并发与重入

### 7.1 失败处置

| 条件 | 必须行为 | 允许的变更状态 |
|---|---|---|
| MCP 缺失/未认证、目标信息缺失、项目/看板/任务歧义 | 询问缺失信息或报告阻塞；不猜测 | 零写入 |
| 权限非 `write`、项目非 Kanban、列缺失/重名/错项目 | 说明人工修正项；不自动补列或改名 | 零写入 |
| 目标 `parentId` 非空，或标题无 active 匹配且未提供 ID | 子任务目标要求顶层父任务；标题无匹配时要求 ID 以区分未找到/已结束 | 零写入 |
| `filter_tasks` 或 completed 分支不可用/截断/capped、日期范围不完整、任一父/子完整读取失败 | 报告无法检查的分支、状态集合与原因；不以另一分支或 undone 快照推断完整 | 零写入 |
| 初始父任务移动结果无法确认 | 先按 §7.2 读回；只有符合瞬时错误与前置状态条件时才允许唯一一次重试，仍无法确认则停止本轮 | 未确认进入 `处理中` 前不创建子任务、不开始任务工作、不进入审查 |
| 工作后的子任务创建/完成失败 | 保留真实本地成果，报告已完成与未同步项；不进入 `待审查` | 父任务保持 `处理中`，不虚假完成子任务 |
| 最终父任务移动失败 | 报告“实际工作已完成，但审查交接未完成”及回读状态 | 不声称整个闭环成功，可安全重入 |
| 发现父任务被外部完成、目标身份变化或子任务列异常变化 | 停止相关写入，保留并报告外部状态；不重开、不回移子任务 | 不再做补偿性写入 |

### 7.2 重试规则

- 普通只读瞬时错误最多重试一次；权限、校验、歧义和完整性错误不重试。遇到限流时尊重服务端给出的等待时间；没有退避信息时不紧密循环，停止并在稍后重入。
- 父任务列更新和子任务完成在结果不明时先按 ID 读回。只有明确为瞬时错误且前置身份/状态仍满足时，才最多重试一次；若读回已是目标状态，则以读回为证据，不重复写入。
- `create_task` 结果不明时**禁止盲目立即重试**。先按 §5.1.6 的 `filter_tasks` active+abandoned 与 completed 两个分支重新枚举该父任务的 child，按父子关系、标题/描述和步骤意图核对；发现已创建项就复用，无法确定、可能重复或任一分支不完整就停止。只有两分支重新读取均证明没有对应项后，下一轮重入才可重新尝试创建。
- 任一写入阶段发生部分成功后，报告必须逐项列出已证实成功的 `taskId + status`（父任务另列 `columnId`）和每个 pending action；不能把后续未执行步骤计入成功。

### 7.3 中断与审查后重入

- **父在 `处理中`**：重新执行全部只读预检与内容读取；不依赖旧会话记忆。已有 `处理中` 状态不重复移动，合适子任务不重复创建，已完成工作不重复执行。
- **父在 `待审查`**：视为等待用户审查，零写入停止；即使上轮曾异常中断，也不替用户决定拉回。
- **父在 `已完成` 或非 active**：零写入停止，不自动重开。需要新轮次时由用户明确恢复目标状态。
- **用户拒绝后**：用户先更新父描述并移回 `处理中`。下一轮以最新描述为准重新检查所有子任务和本地产物，复用仍有效项，为修正工作创建有区分度的新步骤；不自动重开旧完成项，不复制旧计划。
- **旧的已完成子任务仍对应未满足要求**：不把它当作当前完成证据，也不重开；新增具体修正子任务并在实际修复后完成。

## 8. README 与首次使用指引

README 必须替换当前 `待办`/`已完成` 自动同步旧流程，并至少包含：

1. 项目名 `dida-kanbanloop-skill`、单父任务用途和人工审查闭环概览。
2. OpenCode Skill 安装方式：把包含根 `SKILL.md` 的本仓库目录放入用户 OpenCode 使用的 Skills 目录，例如 `~/.config/opencode/skills/dida-kanbanloop-skill/`，随后按所用 OpenCode 版本重新加载/开启会话；不承诺未验证的自动安装器。
3. 已配置且已认证的 Dida365/TickTick MCP 前提，以及目标项目需要读取和写入权限。
4. **醒目且不可遗漏的看板配置**：手工准备 Kanban 列，三个名称精确为 `处理中`、`待审查`、`已完成`，并展示建议显示顺序 `处理中` → `待审查` → `已完成`；Skill 不会自动创建或改名，运行时按列 ID 解析，不强制视觉顺序。必须明确写出“看板可以有其他列；其他列会被忽略且永不被修改”，并说明带空白或近似名称不能替代三个必需列。
5. 调用格式示例，明确提供清单/项目、看板和父任务；缺少信息时 Skill 会询问，标题重复时需要消歧。说明选中子任务会被拒绝，标题无 active 匹配时需用任务 ID 区分“未找到”和“已结束”。
6. 子任务复用/补建（包括复用仍满足要求的已完成项）、`[Agent]` 后缀、实际完成才勾选、子任务不移列、失去必要性时保持未完成并报告，以及本地进度习惯保留。
7. 审查通过和拒绝两套人工操作：通过后用户移到 `已完成`；拒绝后用户更新父描述并移回 `处理中`，再次调用 Skill。
8. MCP 缺失、权限不足、列不匹配、读取不完整、失败/重试和未做实时端到端验证时的说明边界。

## 9. 测试与验证策略

### 9.1 构建期静态检查

使用 Python 3 标准库通过内联命令读取 `SKILL.md` 与 `README.md`，不新增测试依赖或仓库测试脚本。检查：

- 用严格的起始/结束分隔符解析 Skill front matter，含唯一 `name: dida-kanbanloop-skill` 和非空触发描述；两个文件为 UTF-8 Markdown、以换行结尾、无行尾空白，并用大小写不敏感且边界明确的表达式检查 `TBD`/`TODO`/`FIXME`/`PLACEHOLDER`。
- 三个精确列名、`N. <动作> [Agent]`、`[Agent]`、`parentId`、`columnId`、`content`、`desc`、`status = 0`、`status = -1`、`status = 2` 及包括 `filter_tasks` 在内的所有允许 MCP 工具名在 Skill 中可找到。
- README 检查按 §8 的 1～8 项分别覆盖概览、安装、MCP/认证/权限、列规则、调用/消歧、子任务/本地进度、通过/拒绝、故障/验证边界；另查额外列说明和精确配置序列 `处理中` → `待审查` → `已完成`。任何带或不带反引号的 `待办` 及旧 “completed top-level tasks move” 语义都不得存在。
- 静态字符串检查只证明文档契约存在，不冒充行为测试；语义由场景走查与独立审查补足。

### 9.2 场景走查（不调用真实 MCP）

计划必须定义 S1～S14，并要求逐条指出 Skill 中约束它的章节和预期变更账本：缺目标/歧义、MCP/权限失败、额外列与空白/近似列名、完整父子读取（含空描述、abandoned 与用户习惯顺序）、正常首轮、复用活跃及已完成且满足的 child、`[Agent]` 补建、失去必要性、完成前身份复核、最终待审查与排除项报告、限流/退避和部分成功 ID 账本、创建结果不明、中断/拒绝重入、未找到与已结束区分、枚举分支截断，以及把 child 误选为父任务。每个场景的通过条件是：允许的调用顺序、禁止的调用和最终报告均唯一明确。

### 9.3 实时验证边界

只有用户提供或明确授权专用测试清单/看板/父任务后，才可执行真实 MCP 端到端测试；测试应保留每次写入的响应/回读证据并核对子任务列未变。文档构建没有此夹具时必须明确写“未做实时 MCP 端到端验证”，不能以静态检查替代。

## 11. 风险与开放边界

| 风险/边界 | 影响 | 设计缓解 |
|---|---|---|
| `filter_tasks` 无分页参数，completed 查询又受日期/上限影响 | active/abandoned 或 completed 任一分支都可能无法证明“每个子任务”已读取，重入可能重复 | 两分支分别验收完整性；filter 截断即停，completed 采用可靠起点/完整分窗且 capped 即停，不跨分支推断为空 |
| MCP 只暴露项目列，不能独立枚举看板 | 同名项目/多看板可能绑错目标 | 要求用户给出的看板与项目列集合唯一绑定，否则消歧并停止 |
| 提示型 Skill 无法像代码一样强制状态机 | 模型可能误用完成或移动接口 | 非协商不变量、工具白名单、写前守卫、写后证据、场景走查和独立审查 |
| 用户或其他客户端并发编辑 | 旧快照可能导致重复或覆盖审查状态 | 每轮重新读取，写入前核对身份/状态，异常停止；不回移子任务、不重开父任务 |
| 结果不明的创建与限流 | 盲试产生重复子任务或扩大失败 | 创建先 reconciliation、读/写有限重试、遵守退避、保留部分成功账本 |
| 复用现有任务时无法靠改标题/排序表达顺序 | 看板视觉顺序可能与计划顺序不同 | 有序进度清单 + 新建项编号；不为美观修改已有子任务 |
| 不同项目的本地进度习惯不同 | 强制统一文档会干扰现有工作流 | 每次读取目标项目规则和已有习惯，不默认新增进度文件 |
| 无专用实时测试夹具 | 文档 PASS 不等于真实 MCP 行为已验证 | 明确验证边界；首次真实调用保留读回证据，不夸大运行时结论 |

没有需要本轮向用户追加的阻塞性问题；以上假设与停止条件即为安全默认。
